# Command queue shares the session UUID but lives in a separate blob key

Two reasonable shapes existed for bidirectional buffering: (a) one blob keyed by `<session>` with typed entries (`dir: 'in' | 'out'`) sharing the 1 MB cap, or (b) two blobs in the same store — `<session>` for logs, `<session>:cmd` for commands — sharing only the session UUID. We chose **(b)**. Sharing the session keeps the setup story one-step (visit browser → copy one id to `~/.config/gitclip/session` → done) and avoids any new auth identity. Separate keys decouple the lifecycles: log buffer reads stay atomically clear-on-read without disturbing pending commands; the command queue's per-entry dismiss can't accidentally consume log entries; size caps and ETags are independent. The cost is two Blob round-trips on the rare occasion both directions are touched in one tick — fine, since neither endpoint is hot.
