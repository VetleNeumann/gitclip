# Command queue uses per-entry dismiss, not clear-on-read

The existing log buffer (airgapped → Claude) is destructive on read: the act of draining clears the buffer atomically, because Claude is the only consumer and "I sent these to Claude" should mean they're gone. The new command queue (Claude → airgapped) flips the direction, but the consumer (the human at the airgapped browser) needs different semantics: they may copy a command, paste it, watch it fail, copy again, then finally mark it done — so reads must be non-destructive. We chose **per-entry dismiss** (server-assigned UUIDs, `DELETE /api/cmd-dismiss?id=<uuid>`, plus a `clear-all` escape hatch) rather than mirroring the clear-on-read pattern. The asymmetry is deliberate: each direction reflects its consumer's actual workflow, not a desire for surface-level symmetry. A `copied` UI marker (client-side only) bridges the gap between "I grabbed this" and "I'm done with this" without forcing a dismiss-on-copy coupling.
